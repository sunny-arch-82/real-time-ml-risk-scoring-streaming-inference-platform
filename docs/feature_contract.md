# Feature contract riskflow-prior-events-v1
Input timestamp is timezone-aware, whole seconds; UTC feature hour. Unique ID globally; strictly increasing timestamp per account (same-second ties rejected). Current event is excluded from all historical aggregations. Prior-day interval [t−86400,t); hour [t−3600,t); five minutes [t−300,t). Rolling mean/std use population ddof0. Missing history => counts/spend/mean/std0, time-since86400, change flags0, zscore0. Device mismatch compares event's synthetic issuer-provided trusted_device_id; no learned device identity. Category risk lookup is a documented static heuristic, not outcome-trained or a financial claim.
Spark uses integer event-second rangeBetween(-window,-1). Lag flags are ignored when lag is outside24h. Batch/shared Python computes the same formulas; tests compare contracts with tolerances. Spark reads validated local data into driver before real SQL windows, so this version demonstrates distributed-style feature operations, not an end-to-end scalable ingestion design. No large-cluster claim.
Fraud/outcome, raw IDs and timestamps are excluded from model features. Features of validation/test transactions may use earlier events in any prior segment, never labels. Preprocessor fitted only on training. Calibration sees only calibration labels; threshold/selection uses the following validation segment; final test never chooses champion or search parameters. CV uses time-ordered rows within training, gap configurable; sample event generator has unique global timestamps. For arbitrary same-time multiple-account records CV row splits can straddle an identical timestamp; outer train/calibration/validation/test split keeps timestamps together. Grouped temporal CV improvement is future work.
Serving persists event history and cached complete predictions atomically in SQLite; idempotent same-ID retries return the original prediction even after promotion. Reusing ID with altered payload is rejected. Late events are rejected; no watermark/retraction feature correction. Warmup inserts history only; send new later IDs to infer. Batch is isolated and starts cold unless input includes historical context; it never mutates serving state. Kafka uses account keys and three partitions; prediction output is at-least-once and consumers must deduplicate transaction_id/model_version. No exactly-once claim. State retention/expiry is not automatic; per-query24h window limits feature inputs but database grows.

Currency is stable per account; changes without FX normalization are rejected. Included data is USD only. Cross-currency generalization and conversion are not validated.
